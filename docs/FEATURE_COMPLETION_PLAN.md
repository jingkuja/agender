## 补全方案

### 可靠执行与结果回传

增加每任务的 `ExecutionContext`，统一管理截止时间、取消信号、租约状态、已采结果和进度回调。导航、滚动、回复展开、正文抓取每一步都检查它。已经过期的 `deadline_at` 直接终止，不能被最小 30 秒参数裁剪重新延长。软截止停止新动作并保留已有数据，硬截止关闭当前任务页面并有界收尾。

结果状态保持 `running → submitting → acked`。只有匹配任务的有效 `ok=true` ACK 才确认完成；网络故障保留 `submitting` 并退避重放，不重新执行页面操作，也不领取下一任务。服务端确认 409 后转 `superseded`。权限失效、不可重试协议错误与临时故障分别处理。服务端幂等键继续使用 `{task_id}:{attempt}`。

FileClient 与 HTTP 路径采用相同语义：保留每个 attempt 的结果、原子写入、同 attempt 重复提交不覆盖已确认内容；损坏文件隔离，未知任务形成失败回执，避免永久滞留或导致整个 Worker 退出。补上文件 claim 成功而 SQLite 尚未入库时的崩溃恢复窗口。CLI 单次运行直接返回执行结果，解除其对本地 outbox 的依赖，使 HTTP 配置下也能正确报告结果。

### 导航 会话与站点状态

新增共享导航层，返回原始 URL、最终 URL、状态和 HTML。把逐跳策略校验接入真正的网络路径；覆盖浏览器导航、文档跳转、站点切换和 robots 获取，校验必须发生在访问被拒绝地址之前。浏览器自身重定向和域名解析边界需用本地可控服务器验证，不能以“事后检查最终 URL”代替拦截。

按 host 执行可取消的限速等待；沿用当前配置的抖音 6 次/分钟、其它 host 10 次/分钟，定义导航和显式加载动作的计数口径。robots 使用异步 HTTP、缓存和受控跳转。站点连续失败触发冷却，心跳同步移除暂不可用能力，冷却结束通过轻量探测恢复。

会话状态按站点管理，persistent profile 继续作为真相源；备份只用于导入导出。Web 任务期间不使用 Web cookies 判断抖音会话，也不为了心跳切换正在工作的 context。会话 CLI、登录任务和 Worker 共用锁及站点白名单，登录时强制有头的配置覆盖在结束后恢复。能力上报依赖已注册适配器及实际浏览器状态。

### 抖音采集闭环

| 能力 | 实施方式 | 验收要点 |
| --- | --- | --- |
| 短链与详情 | 在允许域内解析分享链接，最多 5 跳；识别最终视频 ID；等待标题、作者或阻断状态 | 普通分享短链能进入详情；越界跳转中止；ID 与 URL 冲突明确报错 |
| 搜索 | 等待卡片，分轮滚动并去重；对排序参数增加枚举和可见 UI 操作 | 数量受上限控制；无结果、加载失败、验证码可区分；不支持的排序不静默忽略 |
| 一级评论 | 打开面板，每轮保存新评论，等待列表变化；处理虚拟列表和加载停滞 | 达到 20 条上限仅表示完成本次限额；不能声明整条视频评论已采全 |
| 二级回复 | `include_replies=true` 时展开可见回复，按每条上限采集；保留父评论关系 | 关闭开关不展开；开启后返回回复；缺失回复数用 null，不伪造 0 |
| 合并任务 | 同一次导航先采视频，再采评论和回复 | 中途超时仍能返回视频及已采评论；不重复打开详情页 |
| 字段完整性 | 解析可见 DOM 和页面已内联 SSR；增加作者、时间、时长、封面等来源 | 每字段可追溯；缺失播放量保留 null 和原因，不以 0 替代 |
| 作者能力 | 新增 `douyin.creator_profile`、`douyin.creator_posts` | 有明确作品数量/时间边界；返回作品列表，后续详情任务由服务端决定 |

新增结果元数据 `stop_reason`、`limit_reached`、`has_more`、`observed_at` 和字段缺失原因。`has_more` 允许未知。只有页面有明确结束证据才设置 `exhausted=true`；无新增但没有结束证据，记录加载停滞。这是对原设计“连续三轮无新增即耗尽”的语义修正，应同步修改协议说明。

请求数量已经满足可为 `succeeded`，同时明确 `limit_reached=true`、`exhausted=false`；因截止或异常提前停止则根据已有数据返回 `partial` 或失败。验证码和登录墙保留 `needs_human`。稳定平台 ID 不可得时使用带视频上下文的去重指纹，并标记 ID 质量，避免把临时 `c_1` 当跨任务唯一 ID。

### Web 研究与热榜质量

保留现有 Bing CN → 百度的一次回退。补充搜索结果跨页去重、重定向后的规范 URL、结果来源与采集时间。文章抽取须区分真实短文、空正文、登录页和验证码页；正文缺失不能自动判 `ok`。截止时保留已完成文章，未开始项目有明确原因，整任务状态反映实际完成度。

热榜使用注册表，将 URL 配置与解析器绑定；只有有解析器、fixture 和健康检查的来源才上报可用。先稳定 `baidu_hot`，移除把所有链接当热榜条目的宽泛回退。再按需求逐个增加来源，每个来源独立返回状态、排名、链接和可得热度。

Web 研究输出补充来源 URL、标题、发布时间、采集时间、正文哈希及提取版本，使服务端可据此生成带证据的研究结果。摘要分析、舆情判断、调度和通知仍由服务端负责。

### 内容存储 导出与增量采集

采用 `ContentStore` 接口，首期提供本地 SQLite 内容库和 JSONL/CSV 导出。运行轨迹库 `agender.db` 保持原有职责；新增独立 `content.db` 保存业务实体，便于单独迁移和清理。后续远端数据库通过同一接口接入。

| 实体 | 最小信息 | 唯一性与更新策略 |
| --- | --- | --- |
| contents | platform、content_id、kind、URL、标题、作者引用、发布时间、首次/最近采集时间 | 有真实 ID 时以平台和 ID 唯一；无 ID 用规范 URL 或标记过的指纹 |
| comments | platform、content_id、comment_id、parent_id、正文、时间、可得互动数 | 同一内容下真实评论 ID 去重；指纹不宣称绝对唯一 |
| creators | platform、creator_id、公开名称、主页 URL、可得统计 | 按平台和作者 ID 更新 |
| metric_snapshots | 内容引用、observed_at、互动数 | 每次观测保留快照，用于变化分析 |
| checkpoints | checkpoint_id、任务参数摘要、站点、采集阶段、已见 ID、结果引用、版本、过期时间 | 仅在数据持久化后更新；不存密码和 cookie |

断点恢复分两层：同一个 attempt 的结果提交重试只重放结果；采集恢复必须由服务端下发新的 attempt，并携带 `resume_from`。Worker 不自行创建或重新执行同一 attempt。恢复校验查询参数、站点、排序和抽取版本，失效断点返回明确原因。

DOM 滚动没有稳定的服务端游标，因此恢复采用“重新打开页面、跳过已见实体、继续有界采集”，不承诺精确回到页面原位置。增量请求增加 `since`、`known_ids` 或内容库过滤；若页面不按时间排序，不能遇到一条旧内容就停止，结果须声明扫描范围。

### 协议 诊断与扩展架构

为现有任务补齐参数 Schema 和类型化结果模型，统一字段语义及错误映射。新增字段先作为可选字段向后兼容；改变现有必填字段、类型或结果语义时明确版本协商与迁移，不能直接给协议换版本号了事。服务端按能力下发新任务，旧任务名继续可用。

执行过程中上报有序且限频的进度：导航、解析、评论滚动、内容保存、结果提交。接入已有事件和 trace 模块，补齐限速等待、重试、断点命中、字段缺失等指标。`capture_html` 采用脱敏、限大小和保留期；登录页面继续禁存敏感产物。若未来启用 HTTP 产物上传，再与服务端共同完成哈希校验、幂等和容量限制。

扩平台时引入 `PlatformAdapter` 与能力注册表，让 BrowserRuntime、SessionManager、Navigator、ContentStore 被各平台复用。先用第二个平台验证扩展方式，再逐个扩展。是否支持搜索、详情、作者、回复须按各适配器实测上报，不能因为类已注册就宣称全能力支持。

## 发布验收与回滚

| 验收层 | 必须覆盖的场景 | 通过标准 |
| --- | --- | --- |
| 协议与执行 | 断网、429、5xx、401、409、ACK=false、过期任务、停止信号、claim 后崩溃 | 不把未确认结果标完成；已确认 409 不再操作页面；同 attempt 不重采；故障过程可追踪 |
| 采集语义 | 登录墙、验证码、空评论、仅部分评论、回复折叠、虚拟列表、选择器改版 | 状态与样本一致；达到限额和真正耗尽分开；未知字段不造数 |
| Web 质量 | 空页、极短正文、重定向、重复结果、robots 拒绝、文章部分失败 | 无伪成功；可用结果不丢失；策略拒绝和截止有明确原因 |
| 内容与增量 | 重复采集、旧断点、排序变化、平台 ID 缺失、统计变化、迁移 | 有 ID 的实体唯一；断点只能恢复匹配请求；版本和保留期可控 |
| 真实站点 | 建议至少 20 个经操作员确认可访问的页面样本，覆盖主要页面状态 | 可访问成功样本必填字段完整；失败样本分类准确；记录实测数量、条件和结果 |
| 持续运行 | 本地动态页面与故障注入 8 小时连续执行，真实站点只做有界抽检 | 没有结果遗失、profile 争用、浏览器泄漏或未解释的心跳中断 |

固定 fixture 的字段及状态正确率要求 100%；真实站点成功率以实际可访问样本测量，报告分母及失败分类，不预先宣称可绕过登录墙或保证所有评论可得。

上线按 FileClient 离线回放 → HTTP mock → 单 Worker 小流量运行推进。每阶段记录任务类型、耗时、字段缺失率、`needs_human` 比例、重复率和结果待提交数。出现结果遗失、协议不兼容或状态误判即停止扩大范围。

回滚前停止领取新任务，保存未 ACK 结果并等待有界收尾；备份运行库和新增内容库。数据库采用明确迁移版本，避免启动时无条件重置 `user_version`。新增能力默认受开关控制，可单独关闭作者、增量或新平台；协议新增字段保持旧调用可用。

## 后续扩展范围

| 扩展 | 建议时机 | 交付边界与预估 |
| --- | --- | --- |
| 第二平台 | 核心版本验收后 | 选择能提供合格公开页样本的平台做试点；注册机制与首个适配器约 7—12 开发人日，样本可行性是前提 |
| 本地操作面板 | 操作员需要频繁看进度、修复会话时 | 复用 Worker 状态、产物与命令；先做只读任务、日志、会话视图，约 4—7 开发人日；不另起浏览器抢 profile |
| 其它热榜来源 | 明确实际研究来源后 | 每来源约 1—2 开发人日加人工样本验证；逐来源启用 |
| 媒体下载 | 存储和使用范围明确后 | 单独设计大小限额、重试、去重和保留策略，重新估算 |
| 云端产物与集中数据库 | 服务端接口就绪后 | 独立联调上传、鉴权、配额、幂等与删除语义，重新估算 |

周期调度、LLM 分析、通知、多租户和多 Worker 控制属于服务端后续项目；本实施计划保留清晰协议边界。首期的完成标准是现有任务真实可用、可中止、可回传、可解释，再以作者和增量能力扩大使用价值。
